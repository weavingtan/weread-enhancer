# 设计文档：文件头（路径 · 行数 · Copy）

日期：2026-11-10
状态：已实现
版本：v0.43.0

## 一、冲突点

GitHub 的文件视图在仓库条下面还有一行：`docs / 第二章 承.md` + `1,284 lines (1,020 loc) · 45.6 KB`
+ `Raw / Copy / Blame`。想补上这一行，会和项目铁律正面冲突：

> 不动正文布局。原生顶栏只是 `opacity: 0` 占位，正文位置与原生严格齐平。

再叠一行 40px 的固定栏，如果正文上方没有对应空白，就会盖住首行文字。而这块空白有多少，
取决于微信读书自己的行距、字号、屏幕高度，**不是一个能写死的常量**。

## 二、方案：有条件地显示，而不是加高正文

1. `.wre-gh-filebar` 是 `position: fixed` 覆盖层，**不推正文**，与侧栏 / 分页条同族。
2. `ghUpdateFilebarFit()` 量两件事：
   - 文件头底边（`getBoundingClientRect().bottom`，量不到就用 CSS 变量算 `顶栏 + 仓库条 + 文件头`）；
   - 正文首行文字的顶边（滚动模式走 `Range.getClientRects()` 取第一个有效文本行；
     翻页模式直接取 canvas 顶边）。
3. 判据：`首行顶边 >= 文件头底边 + 8px` 才显示（`html.wre-gh-filebar-ok`），否则整行不出现。
4. 量不到就当作「放不下」，且**不把结果写进缓存** —— 否则一次测量失败会让文件头到下次切章前
   都不出现。缓存键是 `尺寸签名|当前章`，窗宽/画布/章节变化会自动重测。
5. 显示时侧栏顶部让位（`--wre-gh-filebar-h` 参与 `top` 计算）；退出伪装一并摘掉该 class。

## 三、内容

- 左：`📁 docs / 📄 <章节>.md`（与 file chip、窗口标题同源）。
- 右：`N lines (N loc) · X KB`，取 `.readerChapterContent` 的真实文本（`innerText`，无则
  `textContent`），行数按非空行计，体积按 UTF-8 字节算。
- `Copy`：真复制本章正文到剪贴板，失败给明确 toast（剪贴板权限被拒 / 没读到正文）。
- Notion 皮肤没有这一行（`--wre-gh-filebar-h: 0`，且骨架里没有元素）。

## 四、刻意没做的事

- **不做 `Raw` / `Blame` / `Download` 按钮**：GitHub 文件头确实有，但点了没反应比没有更可疑。
  只保留一个真能用的 `Copy`。
- **不做「已读章节置灰」**：需要每章的已读状态，而微信读书目录里没有稳定可依赖的已读标记，
  猜错比不猜更糟。等抓到真实 DOM 证据再做。

## 五、验收

1. 正文上方空白足够时显示，内容与当前章一致；不足时整行消失，正文不被遮挡。
2. 拖动窗口 / 切双栏切换后重新判定；量不到时不会永久不显示。
3. `Copy` 复制本章正文并弹 toast。
4. 切到 Notion 皮肤不出现文件头；退出伪装不残留位移。
